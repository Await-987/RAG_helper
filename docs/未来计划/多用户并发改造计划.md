## 二、改造目标与指标

### 2.1 性能指标

| 指标 | 当前值 | 目标值 | 说明 |
|------|--------|--------|------|
| **并发用户数** | ~10 | 50+ | 同时在线用户 |
| **并发请求数** | ~5 | 20+ | 同时处理的聊天请求 |
| **单请求响应时间** | 3-10s | ≤10s | P95，含检索+LLM |
| **检索延迟** | 0.5-2s | ≤1s | P95，混合检索+Rerank |
| **GPU 利用率** | 单 Worker | 多 Backend 共享 | 更高效利用 |

### 2.2 可用性指标

| 指标 | 当前值 | 目标值 |
|------|--------|--------|
| **服务可用性** | 单点 | 99%（允许单 Backend 故障） |
| **故障恢复时间** | 手动重启 | ≤30s（自动恢复） |
| **会话一致性** | 100%（单实例） | 100%（多实例） |

### 2.3 验收标准

1. **多 Backend 负载均衡测试通过**
   - 2 个 Backend 同时运行
   - 用户请求轮询分配
   - 对话历史不丢失

2. **并发压测通过**
   - 20 并发请求持续 60 秒
   - 无错误、无超时
   - 响应时间 P95 ≤ 10s

3. **故障切换测试通过**
   - 关闭 1 个 Backend
   - 用户请求自动切换到另一个
   - 新会话正常创建

**推荐方案 B**：改动清晰，彻底解决多 Backend 问题。

### 3.2 方案 B 改动清单

#### 改动 1：ChatAgent 每次从持久化恢复

**文件**：`backend/app/services/chat_service.py`

**改动点**：

```python
# 当前（第 359 行）：
self._sessions: Dict[str, ChatAgent] = {}  # 内存缓存

# 改为：每次请求时从文件恢复，不依赖内存缓存
def get_or_create(self, username: str, session_id: str) -> ChatAgent:
    # 1. 先尝试从 transcript 文件恢复对话历史
    transcript = self._load_session_transcript(username, session_id)
    
    # 2. 如果有历史，重建 ChatAgent 并加载历史
    if transcript and transcript.get("messages"):
        agent = self._create_chat_agent()
        self._restore_history_to_agent(agent, transcript["messages"])
        return agent
    
    # 3. 新会话：创建空白 ChatAgent
    return self._create_chat_agent()

def _restore_history_to_agent(self, agent: ChatAgent, messages: list):
    """从 transcript 恢复对话历史到 ChatAgent"""
    for msg in messages:
        role = msg.get("role")
        content = msg.get("content")
        if role == "user":
            agent.update_memory(
                BaseMessage.make_user_message(role_name="user", content=content),
                OpenAIBackendRole.USER
            )
        elif role == "assistant":
            agent.update_memory(
                BaseMessage.make_assistant_message(role_name="assistant", content=content),
                OpenAIBackentRole.ASSISTANT
            )
```

**改动量**：约 30 行代码

## 四、Docker 部署配置

### 4.1 docker-compose.yml 改动

```yaml
services:
  # Redis：保持不变
  redis:
    image: redis:8-alpine
    command: ["redis-server", "--appendonly", "yes"]
    volumes:
      - ./data/redis:/data
    restart: unless-stopped

  # Qdrant：保持不变
  qdrant:
    image: qdrant/qdrant:latest
    volumes:
      - ./data/qdrant:/qdrant/storage
    restart: unless-stopped

  # Backend-1
  backend-1:
    build:
      context: .
      dockerfile: Dockerfile.backend
    container_name: rag-backend-1
    gpus: all
    env_file: .env
    environment:
      QDRANT_MODE: server
      QDRANT_URL: http://qdrant:6333
      REDIS_URL: redis://redis:6379/0
      SHARED_STORAGE_ROOT: /app/data
      BACKEND_WORKERS: 1
    volumes:
      - ./data:/app/data
      - ./models:/app/models
      - ./.user:/app/.user
    expose:
      - "8000"
    depends_on:
      redis:
        condition: service_healthy
      qdrant:
        condition: service_started
    healthcheck:
      test: ["CMD-SHELL", "curl -fsS http://localhost:8000/health || exit 1"]
      interval: 30s
      timeout: 10s
      retries: 5
      start_period: 90s
    restart: unless-stopped

  # Backend-2（新增）
  backend-2:
    build:
      context: .
      dockerfile: Dockerfile.backend
    container_name: rag-backend-2
    gpus: all
    env_file: .env
    environment:
      QDRANT_MODE: server
      QDRANT_URL: http://qdrant:6333
      REDIS_URL: redis://redis:6379/0
      SHARED_STORAGE_ROOT: /app/data
      BACKEND_WORKERS: 1
    volumes:
      - ./data:/app/data
      - ./models:/app/models
      - ./.user:/app/.user
    expose:
      - "8000"
    depends_on:
      redis:
        condition: service_healthy
      qdrant:
        condition: service_started
    healthcheck:
      test: ["CMD-SHELL", "curl -fsS http://localhost:8000/health || exit 1"]
      interval: 30s
      timeout: 10s
      retries: 5
      start_period: 90s
    restart: unless-stopped

  # Nginx：需要改动 upstream
  web:
    build:
      context: .
      dockerfile: Dockerfile.frontend
    container_name: rag-web
    ports:
      - "${APP_PORT:-8080}:80"
    depends_on:
      backend-1:
        condition: service_healthy
      backend-2:
        condition: service_healthy
    restart: unless-stopped
```

### 4.2 Nginx 负载均衡配置

**文件**：`deploy/nginx/default.conf`

```nginx
upstream backend_cluster {
    # 轮询负载均衡
    server backend-1:8000;
    server backend-2:8000;
    
    # 或使用 least_conn（最少连接优先）
    # least_conn;
}

location /api/ {
    proxy_pass http://backend_cluster;
    
    # SSE 流式响应必须关闭缓冲
    proxy_buffer off;
    proxy_cache off;
    proxy_set_header X-Accel-Buffering no;
    
    # 长连接超时
    proxy_read_timeout 86400s;
    proxy_send_timeout 86400s;
    
    # 传递原始请求信息
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
}
```

## 八、备注

### 8.1 单 GPU 注意事项

如果只有一张 GPU：

- 两 Backend 共享同一 GPU，推理可能排队
- 建议：先单 Backend 测试并发能力，确认瓶颈后再加第二 Backend
- 可通过 `CUDA_VISIBLE_DEVICES` 控制每个 Backend 使用的 GPU

### 8.2 后续优化方向

完成本次改造后，后续可考虑：

| 方向 | 说明 |
|------|------|

| LiteLLM Gateway | 多 LLM Provider 负载均衡 |
| 监控告警 | Prometheus + Grafana |

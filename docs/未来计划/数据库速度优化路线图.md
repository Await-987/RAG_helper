# 数据库速度优化路线图

> 上下文：feat/lxr/update-mineru 分支已修复"导入后未处理数量异常增多"的 bug（去掉 scroll 硬上限 + 在 import/delete 末尾强制重建 BM25 词汇索引）。本文档规划后续如何把数据库增删改查从 O(全库) 提升到 O(增量)。

## 一、当前瓶颈定位

| # | 瓶颈 | 现状 | 影响 |
|---|---|---|---|
| A | 文件管理统计走 pickle 全表遍历 | pickle 1.7 GB，每次刷新都要 `_load_lex_index_from_disk` 解 pickle，再 O(N) 遍历 19 万 payloads | 文件管理页响应慢；pickle 越大越糟 |
| B | `_maybe_build_lex_index(force=True)` 全量 scroll 重建 | 每次 import / delete 末尾都要全量扫 19 万点 | 数据库越大，导入/删除末尾等待越长 |
| C | `delete_by_file_name` 用 `limit=10000` 一次性 scroll | 没有 Qdrant payload index，scroll + filter 是全表扫描 | 删除大文件慢，且 >10000 切片会漏删 |
| D | 增量更新分支永远跑不到 | `save2Qdrant` / `delete_by_file_name` 中 `if self._lex_index_cache:` 永假（因为构造时 `_lex_index_cache = {}`） | 已写好的 O(增量) 代码被废弃，被迫退化成 O(全库) 重建 |

---

## 二、三波优化计划

### 第一波 —— 低成本高收益（强烈推荐）

> 目标：根治 Bug 2 的后果，把所有热路径从 O(全库) 降到 O(变更量)。做完后可以删掉当前的 `force=True` rebuild 兜底。

#### 1. Qdrant payload index on `Original_file`  ★★★★★
- **做法**：服务启动或集合初始化时调用一次：
  ```python
  client.create_payload_index(
      collection_name=collection_name,
      field_name="Original_file",
      field_schema="keyword",
  )
  ```
- **收益**：
  - `delete_by_file_name` 的 filter scroll/delete 从全表扫描 → B+ 树定位，快 **10~100x**
  - 任意按文件名 count 也走索引
- **工作量**：10 分钟
- **风险**：极低；Qdrant 内部索引，对已有数据自动构建

#### 2. 维护独立的 `file_stats.json`（文件名 → 切片数）  ★★★★
- **做法**：
  - 文件位置：`{lex_index_dir}/{collection_name}_file_stats.json`
  - 结构：`{"Original_file_tag": chunk_count, ...}` + `total_chunks: int`
  - 写入时机：
    - `save2Qdrant` 成功后 `stats[tag] += len(records)`
    - `delete_by_file_name` 成功后 `stats[tag] -= deleted_count`，若降到 0 则 `del`
  - 读取时机：`get_database_stats` 直接读 JSON，不再依赖 pickle
- **收益**：
  - 文件管理页响应：秒级 → 毫秒级
  - 解耦：文件管理彻底不依赖 BM25 pickle，搜索/管理两条链路互不干扰
- **工作量**：1~2 小时
- **风险**：
  - 并发写需要加文件锁或用 atomic rename
  - 初次部署需要做一次 reconcile（从 Qdrant scroll 一次生成初始 JSON）

#### 3. lazy-load pickle，让增量分支真正工作  ★★★★
- **做法**：
  - `QdrantDB.__init__` 不动（保持空 cache，避免 1.7 GB IO 阻塞）
  - 在 `save2Qdrant` 和 `delete_by_file_name` 进入前加一个保护：
    ```python
    if not self._lex_index_cache:
        self._load_lex_index_from_disk()  # 失败也继续
    ```
  - 加载成功后 `_lex_index_cache` 非空，原有 `_update_lex_index_for_new_points` / `_update_lex_index_for_deleted_points` 增量逻辑自然生效
- **收益**：
  - 导入 1 个新文件，词汇索引更新从全量重建 19 万 → 增量 N 条（毫秒级）
  - 配合第 1、2 项后，`_run_import_job` 末尾的 `force=True` rebuild **可以删掉**
- **工作量**：30 分钟
- **风险**：
  - 第一次 lazy-load 仍要读 1.7 GB pickle，但仅限于第一次；后续增量极快
  - 多进程并发写 pickle 仍要靠 atomic rename 保护

#### 第一波完成后的效果对比

| 操作 | 当前耗时 | 第一波后耗时 |
|---|---|---|
| 文件管理页刷新 | 几百毫秒~几秒（解 pickle） | 几毫秒（读 JSON） |
| 单文件导入末尾词汇索引同步 | 几十秒（全量重建） | 几十毫秒（增量） |
| 单文件删除 | 几秒（filter scroll） | 几十毫秒（payload index） |
| 关键字检索（keyword_search） | 不变 | 不变 |

### 第二波 —— 进阶优化（如第一波不够再做）

#### 4. 拆分 pickle 为元数据 + BM25 倒排  ★★★
- **背景**：第一波后 file_stats.json 已经替代了 pickle 的元数据角色，但 pickle 内部依然把 `payloads` 完整存了一份（占大头）。
- **做法**：
  - `lex_meta.pkl`（小，KB 级）：doc_ids, doc_lens, avgdl, N
  - `lex_inv.pkl`（大）：inv 倒排
  - `lex_payloads.pkl`（大）：payloads，只在需要返回结果时用
- **收益**：keyword_search 只需要前两个；rerank 之前不读 payload
- **工作量**：2~3 小时

#### 5. 后台异步重建索引  ★★★
- **背景**：第一波做完后正常路径都走增量，但仍需保留一条 force rebuild 兜底（比如 pickle 损坏）。让它在后台跑，不阻塞 import 返回。
- **做法**：
  - 用 `concurrent.futures.ThreadPoolExecutor` 或独立的 worker 进程
  - 加文件锁 `lex_rebuild.lock` 防止并发重建
  - import job 立即标 completed，重建状态单独发布到 `/import-jobs/{id}` 的某字段
- **工作量**：1 小时

### 第三波 —— 架构级（长期方向）

#### 6. 用 Qdrant 原生 sparse vector 替代自维护 BM25  ★★★★★
- **背景**：Qdrant 1.7+ 支持 dense + sparse 混合检索；自维护 1.7 GB pickle 在分布式/多进程下天然容易出问题。
- **做法**：
  - 用 `fastembed` 的 BM25 模型或 SPLADE 模型生成稀疏向量
  - 入库时同时存 dense + sparse vector
  - 检索时用 Qdrant 的 `query_points(prefetch=[dense_query, sparse_query])` 一次性混合
- **收益**：
  - 完全去掉 1.7 GB pickle
  - 删除所有重建/增量/lazy-load 逻辑
  - 检索一次 RPC 完成，省掉 Python 端 BM25 计算
- **工作量**：1~2 天
- **代价**：需要全库重新入库（生成 sparse vector）

## 三、实施顺序建议

```
[已完成] Bug 1 + Bug 2 修复（去 max_scroll + force rebuild 兜底）
   ↓ 部署验证（当前阶段）
[第一波] 1 + 2 + 3 三项（不到一天工作量，根治性能问题）
   ↓ 部署验证
[第一波清理] 删掉 force rebuild 兜底代码
   ↓
[第二波] 4 + 5（如果还有性能反馈）
   ↓
[第三波] 6（架构级重构，未来 mileston）
```

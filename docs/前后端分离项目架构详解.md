# 前后端分离项目架构详解

本文基于当前仓库实际代码整理，描述 `frontend/ + backend/ + tools/` 这一套前后端分离架构如何协同工作。

适用范围：

- React + Vite 前端
- FastAPI 后端
- `tools/` 与 `backend/app/core/` 共享能力层
- 本地文件存储、本地 Qdrant、本地 embedding / reranker / 表格摘要模型

不作为主线的部分：

- 旧 `Streamlit` 入口已移除，不再属于当前主线路径

---

## 1. 架构总览

### 1.1 总体分层

```text
浏览器
  |
  v
frontend/                     React + Vite + Zustand
  |
  | HTTP / SSE
  v
backend/app/                  FastAPI API 层 + Service 层
  |
  +--> app/dependencies.py    模型与服务依赖注入
  +--> app/services/          聊天 / 文件 / 用户 / 鉴权业务
  +--> app/api/v1/            路由入口
  |
  v
backend/app/core/ + tools/    共享核心能力
  |
  +--> backend/app/core/model_runtime.py        LLM / embedding / reranker / 表格摘要
  +--> backend/app/core/agent_factory.py        ChatAgent 工厂与系统提示词
  +--> tools/load_files.py            解析、切块、入库
  +--> tools/mineru_toolkit.py        MinerU 封装
  +--> tools/qdrant.py                向量检索 / 混合检索 / 索引缓存
  +--> tools/database_toolkit.py      给 Agent 暴露的检索工具
  +--> tools/user_auth.py             用户与角色底层能力
  |
  v
data/ + models/
```

### 1.2 核心设计原则

1. 前端只负责展示、交互、状态维护，不直接持有知识库核心逻辑。
2. 后端负责 API、鉴权、会话、长任务协调，但尽量复用已有 `tools/` 和 `backend/app/core/`。
3. 知识库解析、检索、入库等重逻辑放在共享能力层，避免前后端重复实现。
4. 模型路径和数据路径默认以项目根目录为基准，减少“启动目录不同导致路径失效”的问题。

## 3. 前端架构

## 3.1 技术栈

- React
- React Router
- Zustand
- Axios
- Vite

## 3.2 页面组成

当前主要页面：

- `LoginPage`
- `ChatPage`
- `FileManagerPage`
- `UserManagementPage`
- `ChangePasswordPage`

入口在 [frontend/src/App.tsx](/home/ubuntu/rag_project/rag/frontend/src/App.tsx)。

### 3.3 路由与权限控制

前端通过 `ProtectedRoute` 做路由守卫：

1. 首次进入页面时调用 `useAuthStore.getState().checkAuth()`
2. 若未登录则跳转 `/login`
3. 若访问管理员页面但用户不是 `admin`，则重定向到首页
4. 受保护页面统一包在 `MainLayout` 中

这意味着前端权限控制只是第一层，真正的权限判断仍以后端 JWT 与角色检查为准。

### 3.4 状态管理

#### 3.4.1 认证状态

[frontend/src/stores/authStore.ts](/home/ubuntu/rag_project/rag/frontend/src/stores/authStore.ts) 负责：

- 保存 `user`
- 保存 `token`
- 保存 `isAuthenticated`
- 登录后从后端获取当前用户信息
- 刷新页面后通过 `persist` 从本地恢复状态

认证 token 同时会写入 `localStorage` 中的 `access_token`。

#### 3.4.2 聊天状态

[frontend/src/stores/chatStore.ts](/home/ubuntu/rag_project/rag/frontend/src/stores/chatStore.ts) 负责：

- 聊天消息数组
- 当前 `sessionId`
- 流式内容 `streamingContent`
- 流式思考 `streamingReasoning`
- 是否正在请求 `isLoading`

这套状态只存在于前端内存，不做长期持久化。

### 3.5 API 调用层

#### 3.5.1 axios 客户端

[frontend/src/api/client.ts](/home/ubuntu/rag_project/rag/frontend/src/api/client.ts) 统一负责：

- `baseURL=/api/v1`
- 全局超时控制
- 自动注入 `Authorization: Bearer <token>`
- 401 时清理本地登录态并跳转登录页

#### 3.5.2 业务 API 封装

各模块拆分为独立文件：

- `api/auth.ts`
- `api/chat.ts`
- `api/files.ts`
- `api/users.ts`

这样页面层只处理交互，不直接关心 HTTP 细节。

### 3.6 文件预览设计

文件管理页中的预览不是直接把受保护接口 URL 塞进 `iframe`，而是先带 token 拉取 blob，再生成对象 URL 用于预览。

原因：

- `iframe` 直连后端地址不会自动带 axios 拦截器里的 Bearer token
- 需要显式带鉴权头才能访问 `/api/v1/files/content/...`

这是一个典型的“前端展示层需要兼容后端鉴权约束”的实现细节。

## 4. 后端架构

## 4.1 FastAPI 应用入口

[backend/app/main.py](/home/ubuntu/rag_project/rag/backend/app/main.py) 负责：

- 创建 FastAPI 应用
- 配置中间件
- 注册 `api_router`
- 暴露 `/`、`/health`、`/docs`
- 在启动阶段预热文件管理依赖、数据库词汇索引和 reranker
- 在生命周期结束时释放共享数据库工具与表格摘要模型

应用入口的核心角色是“装配器”，不承担业务逻辑。

## 4.2 API 层

路由聚合在 [backend/app/api/v1/router.py](/home/ubuntu/rag_project/rag/backend/app/api/v1/router.py)：

- `auth`
- `chat`
- `files`
- `users`

### 4.2.1 认证接口

[backend/app/api/v1/auth.py](/home/ubuntu/rag_project/rag/backend/app/api/v1/auth.py)

职责：

- 登录
- 获取当前用户
- 登出
- 修改密码

### 4.2.2 聊天接口

[backend/app/api/v1/chat.py](/home/ubuntu/rag_project/rag/backend/app/api/v1/chat.py)

职责：

- 发送聊天消息
- SSE 流式输出
- 清空会话

### 4.2.3 文件接口

[backend/app/api/v1/files.py](/home/ubuntu/rag_project/rag/backend/app/api/v1/files.py)

职责：

- 文件列表
- 上传
- 入库
- 删除
- 内容预览/下载

权限特点：

- 列表和内容预览要求登录
- 上传、入库、删除要求管理员

### 4.2.4 用户接口

[backend/app/api/v1/users.py](/home/ubuntu/rag_project/rag/backend/app/api/v1/users.py)

职责：

- 用户列表
- 创建用户
- 删除用户
- 重置密码
- 修改角色

这部分全部由管理员权限保护。

## 4.3 Service 层

### 4.3.1 AuthService

封装 `tools.user_auth`，提供登录认证与用户读取能力。

### 4.3.2 ChatService

[backend/app/services/chat_service.py](/home/ubuntu/rag_project/rag/backend/app/services/chat_service.py) 是聊天主控层，职责包括：

- 管理会话 ID 与 ChatAgent 实例映射
- 为每个会话维持上下文
- 组装 SSE 输出
- 过滤工具调用噪声
- 汇总 reasoning 与 content

这层的关键价值在于：

- 把 `ChatAgent` 的内部输出转换成前端可消费的流
- 把对话会话生命周期与 HTTP 请求解耦

### 4.3.3 FileService

[backend/app/services/file_service.py](/home/ubuntu/rag_project/rag/backend/app/services/file_service.py) 负责：

- 把 API 层的文件标签转换成绝对路径
- 调用 `tools.file_manager_ui` 做批量入库/删除/统计
- 把结果包装为响应模型

它本身不解析 PDF、不直接操作 Qdrant，而是作为 HTTP 层和共享逻辑层之间的适配器。

### 4.3.4 UserService

负责用户管理相关业务编排，底层仍依赖 `tools.user_auth`。

## 4.4 Schema 层

`backend/app/schemas/` 使用 Pydantic 约束前后端契约：

- `auth.py`
- `chat.py`
- `file.py`
- `user.py`

这一层的价值是：

- 固定请求/响应格式
- 避免前后端字段飘移
- 给 OpenAPI 文档自动生成模型说明

## 4.5 Dependency 层

[backend/app/dependencies.py](/home/ubuntu/rag_project/rag/backend/app/dependencies.py) 是后端的关键装配点，负责：

- `get_current_user`
- `get_current_admin_user`
- `get_auth_service`
- `get_chat_service`
- `get_file_service`
- `get_user_service`
- `get_embedding_model`
- `get_reranker_model`
- `get_database_toolkit`
- `get_table_summary_model`

特点：

1. 服务实例用 `lru_cache` 共享。
2. embedding / reranker / table summary 走模块级缓存。
3. 路由层不直接 new 大对象，而是全部通过依赖注入获取。

## 5. 共享能力层设计

## 5.1 模型装配层 `backend/app/core/`

### 5.1.1 `model_runtime.py`

[backend/app/core/model_runtime.py](/home/ubuntu/rag_project/rag/backend/app/core/model_runtime.py) 提供：

- 主对话模型 `backend_model`
- 流式模型 `stream_model`
- 本地 embedding 模型 `backend_embedding_model`
- reranker 模型 `backend_reranker_model`
- 表格摘要模型初始化与生成

它连接了两类模型来源：

- OpenAI 兼容 API 模型
- 本地磁盘模型

### 5.1.2 `agent_factory.py`

封装 `camel` 的 Agent 能力，为聊天服务提供统一入口。

## 5.2 文档解析与入库层 `tools/`

### 5.2.1 MinerU 封装

[tools/mineru_toolkit.py](/home/ubuntu/rag_project/rag/tools/mineru_toolkit.py)

职责：

- 设置 `MINERU_TOOLS_CONFIG_JSON`
- 解析 `config/mineru.json`
- 将 `models-dir` 解析成绝对路径，避免工作目录变化造成模型找不到
- 调用 pipeline / vlm 两种解析模式
- 输出 `content_list`

### 5.2.2 load_files.py

[tools/load_files.py](/home/ubuntu/rag_project/rag/tools/load_files.py) 是入库主链路，负责：

1. 调用 MinerU 解析 PDF
2. 图片重命名，绑定文档前缀
3. 预处理 `content_list`
4. 生成父子 chunk
5. 组装 metadata
6. 写入 Qdrant

当前实现特点：

- 文件标签 `file_tag` 使用相对项目根目录路径
- 表格、图片、公式等内容都可进入统一 chunk 流程
- 支持表格摘要与表格独立切块
- 不再强制落盘 `content_list.json`

### 5.2.3 file_catalog.py

[backend/app/core/file_catalog.py](/home/ubuntu/rag_project/rag/backend/app/core/file_catalog.py) 虽然名字带 UI，但在前后端分离架构里仍承担很多后端辅助职责：

- 获取本地文件与数据库状态
- 统计每个文件的 chunk 数
- 批量入库
- 批量删除
- 清理数据库统计缓存

它本质上更像“文件管理 domain helper”，不是前端 UI 代码。

### 5.2.4 qdrant.py

[tools/qdrant.py](/home/ubuntu/rag_project/rag/tools/qdrant.py) 负责：

- 初始化本地 QdrantStorage
- 用 embedding 生成向量
- upsert 记录
- 按 `Original_file` 删除
- 语义检索
- 关键词检索索引
- 混合检索与重排

其中一个关键设计是 payload 中保留：

- `Original_file`
- `Content`
- `metadata`

这让前端最终可以回溯到“答案来自哪个原文件”。

### 5.2.5 database_toolkit.py

给 Agent 暴露工具接口，通常是 `search_database` 一类能力。

这层把底层检索逻辑转换成 Agent 可调用的工具协议。

## 6. 数据流

## 6.1 登录链路

```text
LoginPage
  -> authApi.login()
  -> /api/v1/auth/login
  -> AuthService
  -> user_auth 校验用户名密码
  -> 返回 JWT
  -> 前端保存 access_token
  -> authApi.getCurrentUser()
  -> useAuthStore 更新用户态
```

## 6.2 聊天链路

```text
ChatPage
  -> chatApi.streamChat()
  -> /api/v1/chat/stream
  -> ChatService.stream_chat()
  -> SessionManager.get_or_create()
  -> ChatAgent.step(message)
  -> database_toolkit.search_database()
  -> qdrant / reranker / 混合检索
  -> SSE 分块返回 reasoning/content
  -> chatStore 持续更新 UI
```

### 6.2.1 会话机制

- 后端用 `session_id -> ChatAgent` 做内存级会话隔离
- 前端把 `sessionId` 存在 `chatStore`
- 同一会话下，多轮对话共享 Agent 内部记忆

这意味着当前会话是“进程内会话”，不是数据库持久化会话。后端重启后会话丢失。

## 6.3 文件上传与入库链路

```text
FileManagerPage
  -> fileApi.uploadFile()
  -> /api/v1/files/upload
  -> FileService.upload_file()
  -> data/stored_files/

FileManagerPage
  -> fileApi.importFiles()
  -> /api/v1/files/import
  -> FileService.import_files()
  -> tools.file_manager_ui.batch_import_files()
  -> tools.load_files.load_and_store_file()
  -> MinerU 解析 PDF
  -> preprocess / chunk
  -> Qdrant upsert
```

### 6.3.1 文件状态判定

文件管理页面中的“已建库 / 未建库 / ghost”来自本地文件与 Qdrant 中 `Original_file` 的匹配结果：

- `imported`: 本地有文件，数据库里也有对应 chunk
- `not_imported`: 本地有文件，数据库里没有 chunk
- `ghost`: 本地文件已删除，但数据库中仍有残留 chunk

## 6.4 文件预览链路

```text
FileManagerPage
  -> fetch 带 Bearer token 获取 blob
  -> /api/v1/files/content/{file_tag}
  -> FileService.get_file_path()
  -> FileResponse
  -> 前端创建 object URL
  -> iframe 预览
```

## 6.5 用户管理链路

```text
UserManagementPage
  -> usersApi.*
  -> /api/v1/users/*
  -> UserService
  -> tools.user_auth
```

## 8. 当前架构的优点

1. 前后端职责比旧版 Streamlit 方案清晰得多。
2. 现有 `tools/` 和 `backend/app/core/` 基本被复用，迁移成本低。
3. API 契约明确，前端可以独立迭代。
4. 管理员文件管理、用户管理、聊天问答已经拆成清晰模块。
5. 本地模型、本地文件和本地向量库都可离线部署。

---

## 9. 当前架构的边界与风险

## 9.1 进程内会话

聊天会话保存在后端内存中：

- 后端重启会丢失
- 多实例部署时不能天然共享

## 9.2 长任务仍然是同步 HTTP

文件导入、统计刷新、索引更新属于长任务，目前还是同步请求等待结果。

表现为：

- 请求耗时长
- 前端需要放宽超时
- 用户体验依赖单次长连接稳定性

## 9.3 本地 Qdrant 模式扩展性有限

当前是本地 path 模式，点数很多时会出现性能告警。大规模数据下更适合迁移到独立 Qdrant 服务。

## 9.4 共享逻辑仍残留旧命名

例如 `file_catalog.py` 这种模块现在明确归入后端运行时辅助层，语义比旧命名更清晰。

## 10. 推荐演进方向

### 10.1 短期优化

1. 把文件导入改成异步后台任务 + 轮询状态。
2. 把数据库统计改成显式索引任务，而不是每次列表请求都可能触发较重计算。
3. 为聊天会话增加过期清理机制。
4. 为文件入库增加更清晰的任务日志和前端进度展示。

### 10.2 中期优化

1. 将会话历史持久化到数据库或文件存储。
2. 将本地 Qdrant 切换为独立服务部署。
3. 将 `tools/` 进一步按 domain 拆分，例如：
   - `tools/ingest/`
   - `tools/retrieval/`
   - `tools/auth/`
   - `tools/file_management/`

### 10.3 长期优化

1. 将 Agent 编排、检索层、任务队列彻底服务化。
2. 将索引构建、文档解析、检索服务拆成可独立横向扩展的组件。

---

## 11. 一句话总结

这个项目当前的前后端分离架构，本质上是：

“React 前端负责交互，FastAPI 后端负责 API 与会话编排，`tools/` 和 `backend/app/core/` 作为共享知识库能力层，围绕本地文件、MinerU、Qdrant 和本地/远程模型构成完整 RAG 工作流。”

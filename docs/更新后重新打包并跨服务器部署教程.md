# 更新后重新打包并跨服务器部署教程

适用范围：

- 只看当前这个 `rag` 项目，不包含 `LibreChat/`
- 当前项目部署形态是 4 个服务：`web`、`backend`、`qdrant`、`redis`
- 你希望在源服务器更新代码后，重新构建镜像
- 然后把离线部署包放进 `/home/ubuntu/rag_project/rag/deploy_bundle`
- 再把这个目录拷到另一台服务器，直接 `docker load` + `docker compose up -d`

我根据当前仓库实际文件确认过：

- 根部署文件是 [docker-compose.yml](/home/ubuntu/rag_project/rag/docker-compose.yml)
- 后端镜像来自 [Dockerfile.backend](/home/ubuntu/rag_project/rag/Dockerfile.backend)
- 前端镜像来自 [Dockerfile.frontend](/home/ubuntu/rag_project/rag/Dockerfile.frontend)
- 离线部署覆盖文件是 [deploy_bundle/docker-compose.deploy.yml](/home/ubuntu/rag_project/rag/deploy_bundle/docker-compose.deploy.yml)
- 前端 Nginx 反代配置是 [deploy/nginx/default.conf](/home/ubuntu/rag_project/rag/deploy/nginx/default.conf)

当前 `deploy_bundle` 里已经有一套完整离线包，体积大致是：

- `images/` 约 `9.9G`
- `models/` 约 `21G`
- `data/` 约 `26G`

也就是说，完整包接近 `57G`。如果你每次只是代码更新，不一定需要每次都全量搬 `data/` 和 `models/`。

## 1. 先理解这套项目怎么部署

当前项目实际是这 4 个服务：

- `web`
  - Nginx 承载前端静态文件
  - 对外暴露 `${APP_PORT:-8080}`
  - `/api/` 反代到 `backend:8000`
- `backend`
  - FastAPI 服务
  - 依赖 `redis` 和 `qdrant`
  - 默认使用 GPU，`docker-compose.yml` 里写了 `gpus: all`
- `qdrant`
  - 向量库
  - 数据在 `data/qdrant/`
- `redis`
  - 会话索引和轻量状态
  - 数据在 `data/redis/`

所以跨服务器部署时，最少分两类内容：

1. 镜像
2. 运行时文件

运行时文件主要是：

- `.env`
- `docker-compose.yml`
- `docker-compose.deploy.yml`
- `data/`
- `models/`
- `.user/`

## 2. 先决定你这次属于哪一种打包

### 方案 A：完整迁移包

适合这些场景：

- 目标服务器是新机器
- 目标服务器上没有现成的知识库数据
- 你要把当前运行状态整体搬过去

需要带：

- 镜像
- `data/`
- `models/`
- `.user/`
- compose 文件和 `.env`

### 方案 B：只更新代码和镜像

适合这些场景：

- 目标服务器已经有完整的 `data/`、`models/`、`.user/`
- 这次只是后端/前端代码更新
- 不想重复传几十 G 的业务数据和模型

只需要带：

- 镜像
- `docker-compose.yml`
- `docker-compose.deploy.yml`
- `.env`（如果运行配置也变了）

如果你不确定，先按“完整迁移包”做，最稳。

## 3. 源服务器上重新构建镜像

在源服务器执行：

```bash
cd /home/ubuntu/rag_project/rag
docker compose build backend web
```

如果你怀疑 Docker 层缓存会带来旧内容，可以改成：

```bash
cd /home/ubuntu/rag_project/rag
docker compose build --no-cache backend web
```

构建完成后，建议先本机确认能正常跑：

```bash
cd /home/ubuntu/rag_project/rag
docker compose up -d
docker compose ps
docker logs rag-backend --tail 100
docker logs rag-web --tail 50
```

确认没问题后再导出镜像。这样可以避免你把“没启动成功的镜像”打进离线包。

## 4. 给 backend 和 web 镜像打固定 tag

当前 `deploy_bundle/docker-compose.deploy.yml` 里写的是：

- `backend: rag-backend:v2`
- `web: rag-web:v2`
- `redis: redis:v2`
- `qdrant: qdrant:v2`

所以源服务器上建议把刚 build 出来的镜像先打成这两个 tag：

```bash
cd /home/ubuntu/rag_project/rag
docker tag "$(docker compose images -q backend)" rag-backend:v2
docker tag "$(docker compose images -q web)" rag-web:v2
docker tag redis:8-alpine redis:v2
docker tag qdrant/qdrant:latest qdrant:v2
```

可以顺手确认一下：

```bash
docker images | grep -E 'rag-backend|rag-web|redis|qdrant'
```

## 5. 刷新 `deploy_bundle`

如果你想保留之前那一版离线包，先备份：

```bash
cd /home/ubuntu/rag_project/rag
mv deploy_bundle deploy_bundle.bak-$(date +%Y%m%d-%H%M%S)
mkdir -p deploy_bundle/images
```

如果你不需要保留旧包，也至少确保新的 `images/` 会被覆盖刷新。

## 6. 导出 4 个镜像到 `deploy_bundle/images`

执行：

```bash
cd /home/ubuntu/rag_project/rag
mkdir -p deploy_bundle/images

docker save -o deploy_bundle/images/rag-backend-v2.tar rag-backend:v2
docker save -o deploy_bundle/images/rag-web-v2.tar rag-web:v2
docker save -o deploy_bundle/images/redis-v2.tar redis:v2
docker save -o deploy_bundle/images/qdrant-v2.tar qdrant:v2
```

这一步做完以后，目标服务器就不需要源码构建镜像了。

## 7. 复制 compose 和环境文件到 `deploy_bundle`

执行：

```bash
cd /home/ubuntu/rag_project/rag
cp docker-compose.yml deploy_bundle/docker-compose.yml
cp .env deploy_bundle/.env
```

这里说明一下：

- `docker-compose.yml` 是完整原始编排文件
- `docker-compose.deploy.yml` 用来把 `backend` 和 `web` 从 `build:` 切成 `image:`
- 目标服务器启动时用两个 compose 叠加

如果你刚才把旧的 `deploy_bundle` 备份走了，或者你想强制重建这个覆盖文件，就重新生成：

```bash
cat > deploy_bundle/docker-compose.deploy.yml <<'EOF'
services:
  redis:
    image: redis:v2

  qdrant:
    image: qdrant:v2

  backend:
    image: rag-backend:v2
    build: null

  web:
    image: rag-web:v2
    build: null
EOF
```

内容应该保持为：

```yaml
services:
  redis:
    image: redis:v2

  qdrant:
    image: qdrant:v2

  backend:
    image: rag-backend:v2
    build: null

  web:
    image: rag-web:v2
    build: null
```

## 8. 如果做完整迁移，再同步 `data/`、`models/`、`.user/`

完整迁移执行：

```bash
cd /home/ubuntu/rag_project/rag
rsync -a data/ deploy_bundle/data/
rsync -a models/ deploy_bundle/models/
rsync -a .user/ deploy_bundle/.user/
```

这些目录的作用是：

- `data/qdrant/`
  - 知识库向量数据
- `data/redis/`
  - Redis 持久化数据
- `data/stored_files/`
  - 上传的原始文件
- `data/content_lists/`
  - 内容列表
- `data/lex_index/`
  - 词法索引缓存
- `data/chat_sessions/`、`data/agent_memory/`
  - 会话和长期记忆
- `models/`
  - 本地 embedding、reranker、表格摘要模型
- `.user/users.json`
  - 用户账号数据

如果目标服务器本来就已经有这些内容，而且你只是更新代码，那么这一步可以跳过。

## 9. 检查 `deploy_bundle` 是否完整

完整包至少应该像这样：

```text
deploy_bundle/
├── .env
├── docker-compose.yml
├── docker-compose.deploy.yml
├── images/
│   ├── qdrant-v2.tar
│   ├── rag-backend-v2.tar
│   ├── rag-web-v2.tar
│   └── redis-v2.tar
├── data/                # 完整迁移时需要
├── models/              # 完整迁移时需要
└── .user/               # 完整迁移时需要
```

可以执行：

```bash
cd /home/ubuntu/rag_project/rag
find deploy_bundle -maxdepth 2 -type f | sort
```

## 10. 把 `deploy_bundle` 打成压缩包

完整迁移包建议直接打包：

```bash
cd /home/ubuntu/rag_project/rag
tar -czf rag-deploy-bundle-$(date +%Y%m%d).tar.gz deploy_bundle
```

如果目录太大，压缩很慢，也可以直接传目录，不强制一定要 `tar.gz`。

大文件场景下更建议：

- 同机房传输用 `rsync`
- 跨机传输用 `scp` 或 `rsync`

例如：

```bash
rsync -avP /home/ubuntu/rag_project/rag/deploy_bundle user@目标服务器:/home/ubuntu/rag_project/
```

## 11. 目标服务器的前置要求

目标服务器至少要有：

- Docker Engine
- Docker Compose Plugin
- 如果你要跑当前默认配置的 backend，还需要 GPU 和 NVIDIA Container Toolkit

原因是当前 [docker-compose.yml](/home/ubuntu/rag_project/rag/docker-compose.yml) 里 `backend` 写了：

- `gpus: all`
- `NVIDIA_VISIBLE_DEVICES`
- `NVIDIA_DRIVER_CAPABILITIES`

如果目标服务器没有 GPU，要么改 compose 去掉 GPU 配置，要么不要直接照搬当前配置。

## 12. 目标服务器上部署

### 12.1 上传并进入目录

如果你传的是压缩包：

```bash
mkdir -p /home/ubuntu/rag_project
cd /home/ubuntu/rag_project
tar -xzf rag-deploy-bundle-20260420.tar.gz
cd deploy_bundle
```

如果你直接传的是目录：

```bash
cd /home/ubuntu/rag_project/deploy_bundle
```

### 12.2 导入镜像

执行：

```bash
docker load -i images/rag-backend-v2.tar
docker load -i images/rag-web-v2.tar
docker load -i images/redis-v2.tar
docker load -i images/qdrant-v2.tar
```

### 12.3 检查并修改 `.env`

至少检查这些配置：

```env
SECRET_KEY=...
INITIAL_ADMIN_USERNAME=...
INITIAL_ADMIN_PASSWORD=...
OPENAI_API_KEY=...
url=...
MODEL_NAME=...
MAIN_AGENT_MODEL_NAME=...
APP_PORT=8080
conan_path=models/bge-base-zh-v1.5
reranker_path=models/bge-reranker-base
TABLE_SUMMARY_MODEL_PATH=models/Qwen2.5-1.5B-Instruct
```

重点注意：

- `.env` 里的模型服务地址、API Key 很可能需要改成目标环境可用的值
- 如果目标服务器端口不想用 `8080`，就改 `APP_PORT`
- 如果你打的是完整包，`models/...` 这些相对路径通常不用改

### 12.4 启动容器

执行：

```bash
docker compose -f docker-compose.yml -f docker-compose.deploy.yml up -d
```

### 12.5 检查状态

执行：

```bash
docker compose ps
docker logs rag-backend --tail 100
docker logs rag-web --tail 50
curl http://127.0.0.1:${APP_PORT:-8080}/healthz
curl http://127.0.0.1:${APP_PORT:-8080}/health
```

正常情况下：

- `/healthz` 会由 `web` 返回 `ok`
- `/health` 会通过 Nginx 反代到 `backend`

## 13. 如果目标服务器已经在跑旧版本，怎么更新

如果目标服务器已经有上一版 `deploy_bundle`，并且数据目录不想覆盖，建议按这个顺序：

1. 只替换新的镜像 tar
2. 只替换 `docker-compose.yml`、`docker-compose.deploy.yml`
3. 按需替换 `.env`
4. 不动原有 `data/`、`models/`、`.user/`
5. `docker load`
6. `docker compose up -d`

也就是说，目标服务器只做“镜像升级”，不要每次都全量覆盖业务数据。

## 15. 常见问题

### 15.1 `backend` 起不来

优先检查：

- `.env` 中模型接口地址和 Key 是否可用
- 目标服务器是否有 GPU
- 宿主机 `nvidia-smi` 是否正常
- `models/` 是否完整
- `data/qdrant/` 和 `data/redis/` 是否存在权限问题

排查命令：

```bash
docker logs rag-backend --tail 200
docker compose ps
```

### 15.2 页面能开，但接口不通

先检查：

- `backend` 是否 healthy
- `web` 是否启动成功
- `APP_PORT` 是否和防火墙开放端口一致

因为当前 Nginx 配置里：

- `/api/` 转发给 `backend:8000`
- `/health` 也转发给 `backend`

### 15.3 只是代码更新，为什么不建议每次都传完整 `deploy_bundle`

因为你当前完整离线包体积很大：

- 镜像约 `9.9G`
- 模型约 `21G`
- 数据约 `26G`

如果只是改了后端接口或前端页面，真正变化的通常只有：

- `rag-backend-v2.tar`
- `rag-web-v2.tar`
- 少量 compose/.env 文件

这时只更新镜像会更快，也更安全。
